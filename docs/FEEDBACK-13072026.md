## Bugs

| ID      | Status  | Severity | Area    | Description | Notes |
| ------- | ------- | -------- | ------- | ----------- | ----- |
| BUG-009 | TESTING | Medium   | Invoice | A `?` appears in front of every discount amount on the invoice and receipt. | Root cause: the minus sign is U+2212, written into a monospace cell; dompdf's DejaVu Sans Mono has no glyph for it and falls back to `?`. Fixed by using an ASCII `-`. |
| BUG-010 | TESTING | High     | Invoice | A record with many services overflows the PDF and a service block splits across the page boundary mid-way. | Root cause: one tall card per service, and no `page-break-inside` rule. Fixed by the line-item table (CHG-030) plus explicit page-break rules. |
| BUG-011 | TESTING | High     | Invoice | Editing a pending service record did not update its invoice. If anyone had already opened the invoice, it kept showing the old services and total forever — while the payment page charged the new amount. | Found while reviewing this batch, not reported. The invoice is minted and frozen on first view; `update()` rewrote the lines and the transaction but never the invoice. Now re-freezes against the corrected record, keeping the same `INV-` number so a customer holding that reference sees the corrected figures. |
| BUG-012 | TESTING | Medium   | Invoice | A discount larger than its line total was accepted. The line's subtotal floors at zero, so the invoice printed e.g. `Subtotal RM 370.00 / Discount - RM 500.00 / AMOUNT DUE RM 0.00` — totals that don't add up. | Found while reviewing this batch, not reported. `discount` was validated `min:0` with no upper bound. Now rejected against the **server-side** rate (the fee book price, not the rate the form submits), and the error shows on the discount field. A discount exactly equal to the line total is still allowed — a full write-off is legitimate. |
